# 排错与固件选型笔记

> 本文记录这台 Air780EPV 短信转发器从"跑几小时就失效"到"五层自愈 + 持久化"的全过程。
> 所有结论都标注了来源：**实测**（在真机上验证过）、**引用**（有公开资料）、**推断**（没有直接证据）。
> 设备：Air780EPV_A12 / 芯片 EC718PV / 联通 460-01 / Band 3。

---

## 一、设备与固件事实

| 项目 | 值 | 来源 |
|---|---|---|
| 芯片 | EC718PV（Cat.1 bis，R13/R14，集成 BB+RF+PMIC） | 实测 `am_get_chip_type`；[移芯官网](http://www.eigencomm.com/cn/Content/3006141.html) |
| 模组 | Air780EPV_A12 | 实测 |
| 官方固件 | EPV 正式版止于 `V1002_EC718PV`，之后需云编译 | [合宙固件下载页](https://docs.openluat.com/air780ep/luatos/firmware/) |
| 云编译入口 | luatos.com → 在线编译，芯片选 `@EC718PV` | [云编译](https://luatos.com/zh_cn/my/build.html) |
| 脚本区 | V1002/V2002/V2003 = 128 KB；V2001 = 64 KB | 实测（解包 `.soc` 读 `info.json`） |
| Lua 堆 | 128 KB（`chip.ram.lua`），系统 256 KB | 实测 |

> **`.soc` 其实是 7z 压缩包**，里面含 `info.json`（分区表）、`luat_conf_bsp.h`（编译开关）、`luatos.binpkg`（固件镜像）。
> 本仓库的 `tools/soc_inspect.ps1` 就是解包读这两个文件来判断固件能力。

## 二、四类故障与结论

### 1. 数据面僵死（HTTP 全部超时，重启才恢复）

**现象**：运行约 23~24 小时后，短信能收、电话能通，但 `http.request` 全部返回 `-8`（超时）。

**证据链**：

- 断电重启后立刻恢复 → 不是账号/流量/信号问题
- 两次故障间隔都是 23~24 小时（2026-11-24、11-26）→ 与运行时长强相关
- 同期 `SMS` 接收也失效，两个子系统同时死、同时活 → 判断为模组运行态劣化（**推断**）

**社区同类问题**：

- [I9BUOL 经常断网](https://gitee.com/openLuat/LuatOS/issues/I9BUOL)
- [IK730Q Air780EPM 偶尔无法收发短信【不能稳定重现】](https://gitee.com/openLuat/LuatOS/issues/IK730Q)

**对策**：见第四节（五层自愈）。

### 2. SMS 接收失效（新短信完全不触发回调）

**现象**：灯显示正常（慢闪），但新发的短信不触发 `sms.setNewSmsCb`，Lua 层完全无感知。

**关键约束**：**设备无法自己发现"我收不到短信了"**——"没有短信"和"短信没送到"在 Lua 层完全一样。

**社区线索**：

- [I8EZOA SIM 卡里有未读 SMS 时，新短信不触发回调](https://gitee.com/openLuat/LuatOS/issues/I8EZOA)
- [IAGVYZ V1002_EC718PV 不支持电信短信](https://gitee.com/openLuat/LuatOS/issues/IAGVYZ)

> 但实测**重启能恢复**，而重启不会删除 SIM 卡里的未读短信 → "未读阻挡"假说被削弱（**推断**：更像 SMS 子系统运行态失效）。

**对策**：无法直接探测，只能用数据面做代理指标（见第四节第 5 层）。

### 3. USB 枚举抖动导致整机复位（调试期假故障）

**现象**：接着电脑调试时，日志里每秒出现

```
print com USB 断开连接 COM4  CommError,[WinError 22]
soc log port COM4 打开成功
```

随后设备静默复位（无任何错误日志）。

**结论（实测）**：V2003 固件存在此缺陷，合宙在 **V2024** 的更新说明中修复：

> update: log, 优化 log 输出，不会出现因软复位开机打印频繁，或者 **USB 插拔（或枚举丢失又重连）太频繁都会触发的看门狗重启**。

来源：[Air780EP 固件更新说明](https://docs.openluat.com/air780ep/luatos/firmware/)

**对策**：烧录/调试期间关闭「4G模块USB打印」；不要长期挂 USB。

### 4. 压测误判（100 次失败请求 ≠ 会崩）

最初用 100 次失败请求压测，接 USB 时在 640 秒处静默复位，一度误判为"HTTP 库被失败请求毒死"。

**拔掉 USB 后重跑同样压测：不崩，且通道仍可正常推送。**

**修正结论（实测）**：那次复位是 USB 枚举 bug（见第 3 条），与 HTTP 请求次数无关。

## 三、固件对比与选型

| 固件 | 来源 | 脚本区 | FSKV | UART | VoLTE | TLS |
|---|---|---|---|---|---|---|
| V2003_EC718PV | 第三方云编译（原设备自带） | 128 KB | ❌ | ❌ | ✅ | 未知 |
| V2002_EC718PV_CLOUD | 第三方云编译 | 128 KB | ❌ | ❌ | ✅ | ❌ |
| **V1002_EC718PV** | **合宙官方最后一版** | 128 KB | ✅ | ✅ | ✅ | ❌ |
| V2001_EC718PV_CLOUD | 第三方云编译（[lageev](https://github.com/lageev/air780e-forwarder) 仓库附带） | 64 KB | ✅ | ✅ | ✅ | ❌ |

> 以上 FSKV/UART/TLS/VoLTE 四列均为**实测**：解包 `.soc` 读 `luat_conf_bsp.h` 的 `LUAT_USE_*` 宏。

**选型建议**：

- 要**持久化队列**和 **AT 通道** → V1002 或 V2001（两者都有）
- 要**脚本空间**（128 KB）且来源可靠 → **V1002**（官方发行版）
- 要**更新的内核**（但脚本区只有 64 KB）→ V2001

**本设备当前使用**：V2001_CLOUD（base 23.11 / bsp V2001 / Build 2024-12-01），因为作者社区长期验证，且换固件是单向操作，选了实践数据更多的那一个。

> **TLS 全部未编译**：两个可得的 EPV 固件里 `LUAT_USE_TLS` 都是注释状态，**HTTPS 不可用，只能用 http://**。

## 四、五层自愈（当前实现）

| 层 | 手段 | 触发条件 | 代价 |
|---|---|---|---|
| 1 | 固件自动重注册 `mobile.setAuto(10000, 30000, 8, true, 60000)` | 掉网后 30 秒 | 无 |
| 2 | 定时切飞行模式 `mobile.reset()` + flymode on/off | 每 12 小时 | 约 2 秒断网 |
| 3 | **失败后切飞行模式** | 连续失败 2 次 | 约 2 秒断网 |
| 4 | 重启整机 `rtos.restart()` | 连续失败 6 次 | 约 60 秒（队列已落盘不丢） |
| 5 | 定时重启 | 运行满 23 小时 | 约 60 秒（队列不丢） |

第 2、3 层的节奏参考 [lageev/air780e-forwarder](https://github.com/lageev/air780e-forwarder)（136 stars，长期维护）：

```lua
-- 他的实现：每连续失败 2 次，重建一次协议栈
if error_count % 2 == 0 then
    mobile.reset()
    mobile.flymode(0, true)
    mobile.flymode(0, false)
end
```

> ⚠️ 另一个项目的注释里警告过"应用层切飞行模式会和固件自愈抢射频，酿成死亡螺旋"（[jswmcy/air780epv-forwarder](https://github.com/jswmcy/air780epv-forwarder) 的 `util_watchdog.lua`）。
> 但那针对的是**高频切换**（每 2 分钟）。本项目是 **12 小时一次 + 失败触发且限制最小间隔 60 秒**，量级不同。

**仍待观察**：这套自愈能否覆盖第 2 类故障（SMS 接收失效）——Lua 层无法感知，只能靠第 3、4 层在"有消息发不出去"时兜住。

## 五、为什么这不是脚本的 bug（证据）

| 现象 | 排除过程 |
|---|---|
| "缺库导致功能不可用" | 实为 `_G` 不可靠 + 库是 userdata，`type(x)=="table"` 判断错误 |
| "跑几小时就崩" | 用 `[dump]` 打印 API、`pcall` 兜住所有任务体后，崩溃消失 |
| "100 次失败请求会崩" | 拔掉 USB 后复测不崩，真凶是 USB 枚举 bug |
| "重启丢短信" | 换到带 `fskv` 的固件后，实测重启能补发（见下） |

**持久化实测记录（2026-11-26）**：

```
17:19:39  [sms]  from=10655158  len=139     ← 139 字长短信
17:19:39  [sms]  已入队, pending=1
          （人为拔电）
17:19:48  [main] sms-forwarder 4.0.0 V2001
17:19:48  [queue] fskv 可用，队列持久化
17:19:48  [queue] ready, pending=1          ← 队列从 Flash 恢复
17:19:50  [push] 已受理 ... → 成功, 剩余=0    ← 启动后 2.5 秒补发
```

## 六、脚本层面的踩坑清单

| # | 坑 | 现象 | 正确做法 |
|---|---|---|---|
| 1 | `_G[name]` 读不到库 | 能力探测全报缺失，但库明明能用 | 直接读全局变量 |
| 2 | 库是 userdata 不是 table | `type(sms)=="table"` 误判成"没有 sms" | 用 `pcall` 取字段（本项目 `util_lib.lua`） |
| 3 | 未捕获错误 = VM 退出 | 一个异常 → 整机 15 秒后重启，且循环 | 任务体、回调体全部 `pcall` |
| 4 | 超时 > 看门狗 | 网络一卡就重启，永远看不到超时错误码 | HTTP 超时 6 秒 < 看门狗 10 秒 |
| 5 | 定时重启掩盖问题 | 每天漏 1 分钟短信 | 优先"按症状重启"，且队列必须落盘 |
| 6 | 应用层切飞行模式（高频） | 与固件自愈抢射频，可能死亡螺旋 | 只做低频（12 小时）或失败触发 |
| 7 | pushplus txt 模板换行被吞 | 邮件挤成一行 | `template=html` + `<br/>`，参考[官方说明](https://www.pushplus.plus/doc/help/line.html) |
| 8 | pushplus 返回 200 ≠ 已送达 | 以为发出去了其实没有 | 只是"已受理"，投递异步，见[邮件渠道说明](https://www.pushplus.plus/doc/extend/mail.html) |
